# ライティングスタイルガイド

> 記事執筆時はこのスタイルを徹底的に再現する。

## 冒頭パターン

挨拶から始めない。noteのプレビューで見える最初の3行を、読者の課題・違和感・問いに使う。

必ず以下のいずれかで始める:

### パターンA: 現場の違和感から始める
```
（現場でよくある違和感・困りごとを1〜2文）
（なぜそれが問題なのかを続ける）

```

### パターンB: いきなりフック
```
（衝撃的な事実 or 疑問 or シーン描写で始める）
（2〜3文で読者を引き込む）
```

### パターンC: 格言調で始める
```
○○とは、△△することである。
ー MasterZ

（本文。格言の意味を、現場の困りごとや具体例に引き寄せて説明する）
```

- noteのプレビュー3行を強く使いたいときに有効
- 実在人物の名前を付ける場合は、実際の引用として確認できるものだけにする
- 未確認の言葉は、実在人物の発言のように見せない。`ー MasterZ`、または出典なしの一文として使う
- 格言だけで終わらせず、直後の本文で必ず実務の話に戻す

## 文章リズムのルール

### 最新の優先ルール

- 1行ごとの改行はしない。意味のまとまりごとに段落を作る
- 冒頭に「こんにちは」「はじめまして」「久しぶりに書いています」などの挨拶を置かない
- スマホ最適化の余白より、文章の内容と論理の流れを優先する
- 段落のまとまり + 改行 + 強調文で、もっとも言いたいことを1行で表す
- 余白で読ませるより、接続・因果・前提・結論が自然につながる文章を優先する
- 意味の分からない文章は書かない。抽象語を使うときは、直後に具体例・業務場面・判断基準へ落とす
- 「笑」「顔文字」「P.S.」は使わない

### 分かる文章の基準

抽象的な文章を書いたら、直後に「つまり、現場では何が起きるのか」「読者は何を見直せばよいのか」まで書く。

悪い例:
```
本質的な価値提供によって、組織の可能性を最大化することが重要です。
```

よい例:
```
業務効率化で大事なのは、作業を減らすことだけではありません。
誰が、どの判断に時間を使っているのかを見えるようにすることです。

たとえば見積書の作成なら、AIに任せられるのは文章のたたき台や表の整理です。
でも、値引きしてよいか、どの条件を優先するかは、人間が判断する必要があります。
```

### 格言調の使い方

テーマの核心を、短い定義文として言い切る。

```
効率化とは、人間の判断を消すことではない。
人間が判断すべき場所を、見えるようにすることである。
ー MasterZ

AIを入れるときに、最初に考えるべきことがあります。
それは「何をAIに任せるか」ではありません。
「どこに人間の判断が残っているか」です。
```

使いどころ:
- 冒頭のフック
- 大きな章の前
- 結論に入る直前
- 具体例から抽象化するとき

注意:
- 1記事に1〜3回までにする
- 格言だけを浮かせず、直後に本文で意味を回収する
- きれいな言葉より、記事の論理を前に進める言葉を優先する
- 実在人物への未確認の引用 attribution はしない

### 短文 → 短文 → 太字 のリズム
```
これは、驚いた。

普通のAIって、何も言わずに「やって」と頼むと、そのまま作業を始めようとするじゃないですか。
でもAIは「まず認識を揃えさせてください」から入ってきた。

**優秀なコンサルタントとか、できる部下がやる仕事と同じなんですよね。**
```

### 問いかけ → 即答え パターン
```
なぜ、AIを入れても仕事が楽にならないのか？

ツールが悪い？→もっと高機能なものはある
使う人が悪い？→真面目に使おうとしている人も多い
会社の理解が足りない？→それもあるけれど、原因はそこだけではない

本当の問題は、任せる前の仕事の分解ができていないことにある。

**AIに任せる前に、人間が何を判断しているのかを分ける必要がある。**
```

### 箇条書きの畳み掛け
```
* 入力する情報が足りない
* 判断基準が決まっていない
* 誰が確認するかも決まっていない
* 例外処理だけが担当者の頭の中にある
* その状態でAIに任せようとしている
```

### 一文独立の強調
```
**AI化の前に、まず分けるべきものは3つあります。**

1. AIに任せてよい作業
2. 人が確認すべき判断
3. そもそもやめてもよい手順
```

## 太字（**bold**）の使い方

記事の読みどころを作るために使う。以下の場面で使う:
- **核心メッセージ**: その段落で一番言いたいこと
- **転換点**: 「でもね、ここに一つ、重要な前提がある。」
- **結論**: 「**AIに任せる前に、人間が何を判断しているのかを分ける必要がある。**」
- **独立した強調文**: 1〜2行を太字にして独立させる

太字は多用してよいが、装飾ではなく論理の節目に使う。

## 改行・空白の使い方

- 一文ごとの機械的な改行はしない
- 段落は意味のまとまりで分ける
- セクション間は空行1つを基本にする
- 重要な文だけを独立させる。余白は論理の転換や感情の山場に限定する
- スマホで読みやすくするためだけの過剰な空白は避ける

## 語尾パターン集

| 場面 | 語尾例 |
|------|--------|
| カジュアル | 〜なんですよね。/ 〜なわけです。/ 〜でしょ？ |
| ツッコミ | 〜では？/ 〜なんだよな。/ 〜ですよね。 |
| 断言 | 〜です。断言します。/ 〜なんです。 |
| 問いかけ | 〜じゃない？/ 〜だと思いませんか？ |
| 自虐 | 〜でした。(その節はごめん。) |
| 感嘆 | 〜やばい。/ 〜最高じゃない？ |

## 「笑」の扱い

- 「笑」は使わない
- ユーモアは、比喩・言い換え・セルフツッコミ・文脈のズレで表現する
- 照れ隠しの語尾に頼らず、言い切るか、少し柔らかい一文に置き換える

## 構成パターン（記事タイプ別）

## 以下は記事構成の参考パターン

### TYPE A: 体験レビュー型
1. 「実際に○○を試してみた」で始める
2. 時系列で体験を語る（臨場感重視）
3. 使い方をステップ化してまとめる
4. 「なぜこれがすごいのか」を技術的に解説
5. 読者の業務にどう使えるかへ接続する

### TYPE B: 業務改善・考え方整理型
1. 現場で起きている困りごとを提示する
2. よくある誤解や雑な解決策を整理する
3. 問題の正体を分解する
4. AI・IT・手順化で解決できる部分を示す
5. 人が判断すべき部分を残す
6. 読者が明日確認できる問いで締める

### TYPE C: 経験共有型
1. 過去の現場経験や支援経験から入る
2. 当時の課題と、今も残っている課題をつなげる
3. 変わったものと変わっていないものを分ける
4. 今ならAIやITでどう扱えるかを示す
5. 読者の現場に置き換えられる形で締める

### TYPE D: 提案・チェックリスト型
1. 読者が判断に迷う場面を提示する
2. 判断軸を3〜5個に整理する
3. 具体例で使い方を説明する
4. AIに任せる部分と人が確認する部分を分ける
5. 必要に応じて有料記事・資料・個別相談への導線を置く

```
「おわりに」の文章には、かならず最初の問いを含める。

```

## noteエディタのフォーマット制約

noteのテキストエディタで使える記法は以下のみ。記事を書くときはこの制約内で書くこと。

| 記法 | ショートカット | 備考 |
|------|--------------|------|
| 見出し | `# ` + スペース | 大見出し。noteでは `##` 以降の見出しレベルはない |
| 小見出し | `## ` + スペース | 小見出し。`###` は使えない（noteでは反映されない） |
| 箇条書きリスト | `- ` or `+ ` or `* ` + スペース | |
| 番号付きリスト | `1. ` or `2) ` + スペース | |
| 引用ブロック | `> ` or `>> ` + スペース | |
| 太字 | テキスト選択 → B | `**太字**` のMarkdown記法は使えない |
| 区切り線 | `---` | |

### 重要な制約

- **`###` 以下の見出しは使えない**: noteでは `#`（見出し）と `##`（小見出し）の2段階のみ
- **太字のMarkdown記法 `**text**` は使えない**: noteエディタ上ではテキスト選択 → Bで太字にする
- **テーブル（表）は使えない**: noteのエディタにはテーブル機能がない。代わりに箇条書きや本文で表現する
- **コードブロックは使えない**: `` ``` `` 記法はnoteに存在しない
- **画像はエディタ上で挿入**: Markdownの `![alt](url)` は使えない

### 下書きファイルの書き方ルール

下書きMarkdownファイルでは `**太字**` は使ってOK（読みやすさのため）。
ただし、**noteに貼り付けるときに以下の変換が必要**であることを意識する:

- 見出しは下書き段階でも `#` と `##` までにする
- `**太字**` → noteエディタ上で手動で太字にする
- テーブル → 箇条書きに変換
- コードブロック → 引用ブロック or 本文に変換

## NGパターン（これをやったらMasterZぽくない）

- 「〜させていただきます」的な丁寧すぎる敬語
- 一文が80文字を超える長文
- 冒頭が挨拶や自己紹介で始まっている
- 見出しが「1. はじめに」「2. 本論」みたいな教科書スタイル
- 太字が全く使われていない
- 太字が装飾になっていて、論理の節目を示していない
- 格言調の一文が本文とつながっておらず、雰囲気だけになっている
- 未確認の言葉を実在人物の名言のように見せている
- 抽象語だけが並び、読者が意味を具体的に理解できない
- 「本質」「価値」「可能性」「最適化」「変革」などの言葉を、具体例なしで使っている
- 一文ごとに機械的に改行している
- 余白を優先しすぎて、論理の流れが切れている
- 段落が長すぎて読みづらい
- `###` 以下の見出しを使っている
- P.S. / P.P.S. / P.P.P.S. を使っている
- 「笑」や顔文字を使っている
- 体験談やエピソードが一切ない
