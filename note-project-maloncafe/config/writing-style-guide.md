# ライティングスタイルガイド

> 記事執筆時はこのスタイルを徹底的に再現する。

## 冒頭パターン

基本は以下のどちらかで始める。現行運用では、一覧で見える最初の1行を最優先する。

### パターンA: 定番オープニング
```
（必要な場合だけ短いあいさつ）
（状況・背景を1〜2文）

```

### パターンB: いきなりフック
```
（衝撃的な事実 or 疑問 or シーン描写で始める）
（2〜3文で読者を引き込む）
```

## インプレッションを増やす入口設計

本文が良くても、タイトル・冒頭・タグが弱いと読まれる前に止まる。フォローやスキが増えていない記事は、本文の深さ以前に「表示される入口」と「開きたくなる入口」を見直す。

### タイトルの役割

タイトルは、記事内容の要約ではなく「読む理由」を作る場所。抽象的なテーマ名ではなく、読者が自分の問題として反応できる形にする。

弱いタイトル:

```
AIと文章について考えたこと
人生後半の人間関係
note収益化の考察
```

強くする方向:

```
なぜ、AIを使うほど文章が浅くなる人がいるのか
人生後半、人間関係を減らしても孤独が軽くならない理由
noteを書き続けてもスキが増えない人が見落としている入口
```

タイトルを作るときは、次のどれかを入れる:

- 読者の悩み: 「なぜ〇〇できないのか」
- 分岐: 「〇〇できる人と、できない人の違い」
- 違和感: 「〇〇なのに、なぜ△△なのか」
- 具体場面: 「〇〇したときに起きる△△」
- 読後利益: 「〇〇を軽くする考え方」

### 冒頭の役割

冒頭は、本文への助走ではなく離脱を止める場所。最初の3〜5文で、読者に「これは自分の話だ」と思わせる。

冒頭でやること:

1. 読者が経験していそうな場面を出す
2. そのときの感情や違和感を代弁する
3. よくある解決策を一度出す
4. 「でも、たぶん問題はそこじゃない」と再定義する
5. この記事で扱う問いを出す

弱い冒頭:

```
今日はAIと文章について考えてみます。
最近、AIを使う人が増えています。
```

強くする方向:

```
AIに文章を書かせると、たしかに速い。
でも、読み返したときに「これ、自分の文章じゃないな」と感じることがある。
文章量は増えたのに、なぜか思考が浅くなった気がする。

たぶん問題は、AIを使うことそのものではない。
AIに渡す前の問いが、まだ浅いままなのだと思う。
```

### タグの役割

タグは、記事を見つけてもらうための入口。自分が言いたい概念だけではなく、読者が実際に探しそうな言葉を混ぜる。

タグは次の3種類を組み合わせる:

- 大きいタグ: `#note`、`#AI`、`#仕事`、`#人生`、`#人間関係`
- 読者の悩みタグ: `#文章術`、`#発信`、`#副業`、`#定年後`、`#キャリア`
- 記事固有タグ: 記事の中心テーマ、独自概念、具体的な対象読者

タグ選びの注意:

- 独自すぎる言葉だけにしない
- 広すぎるタグだけにしない
- 記事内容と関係ないタグを入れない
- タイトルに入れた主要語と近いタグを入れる
- 読者が検索しそうな普通の言葉を優先する

### 公開前チェック

公開前に、本文を直す前にまずここを見る:

1. タイトルだけで、誰のどんな悩みの記事かわかるか
2. 冒頭3〜5文で「自分の話だ」と思えるか
3. タグに、読者が探しそうな普通の言葉が入っているか
4. タイトル・冒頭・タグの言葉がズレていないか
5. 読後に何を持ち帰れる記事か、冒頭でうっすら見えるか

## 文章リズムのルール

### 短文 → 短文 → 太字 のリズム
```
これは、ほんとうに驚いた。

普通のAIって、言われたことをそのままやろうとするじゃないですか。
でもAIは「まず認識を揃えさせてください」から入ってきた。

**優秀なコンサルタントとか、できる部下がやる仕事と同じなんですよね。**
```

### 問いかけ → 即答え パターン
```
なぜ特定の人に恋をする？

顔？→もっと美人/イケメンはいる
性格？→もっと優しい人はいる
スペック？→もっと高収入はいる

でも「この人じゃなきゃダメ」になる。

それはなぜか？

**共有した時間と経験が代替不可能性をもたらすから。**
```

### 箇条書きの畳み掛け
```
* 「もっといいものを逃してるかも」
* この恐怖が、現代人を支配してる。
* 恋人といても、他のカップルが気になる。
* 仕事してても、他の会社が気になる。
* 何を選んでも、不安。
```

### 一文独立の強調
```
**これを、本気で推してる人だいたい3パターン：**

1. 実践してない人（口だけ）
2. 搾取されて病んでる人（共依存）
3. 搾取してる側（「もっと愛して！」）
```

## 太字（**bold**）の使い方

記事の最大の特徴。以下の場面で使う:
- **核心メッセージ**: その段落で一番言いたいこと
- **転換点**: 「でもね、ここに一つ、重要な前提がある。」
- **結論**: 「**代替不可能だと信じること。それこそが、愛の本質だ。**」
- **独立した強調文**: 2〜3行を太字にして独立させる

## 改行・空白の使い方

- １行ごとに改行しない。（段落単位で読む）
- スマホ最適化よりも、文章の内容と論理の流れを優先する
- 空白を空けすぎない。散文や詩のように見せない
- セクション間は改行１つ
- 重要な文の前後だけ、必要に応じて空行を使う
- 短い段落を基本にしつつ、1文ごとの過剰な分断は避ける

## 語尾パターン集

| 場面 | 語尾例 |
|------|--------|
| カジュアル | 〜なんですよね。/ 〜なわけです。/ 〜でしょ？ |
| ツッコミ | 〜では？/ 〜なんだよな。/ 〜ですよね。 |
| 断言 | 〜です。断言します。/ 〜なんです。 |
| 問いかけ | 〜じゃない？/ 〜だと思いませんか？ |
| 自虐 | 〜でした。(その節はごめん。) |
| 感嘆 | 〜やばい。/ 〜最高じゃない？ |

## 「笑」の扱い

- 「笑」は使わない
- 自虐やツッコミは、語尾・間・文脈で出す
- 照れ隠しのための「笑」も入れない

## 有料・無料どちらにも使える収益化記事テンプレート

有料記事だけを特別扱いしない。無料記事でも有料記事でも、読者が「これは自分の話だ」と感じ、続きを読みたくなり、読後にひとつ視点や行動を持ち帰れる構造にする。

ただし、有料化を急がない。フォローやスキが安定して増えていない段階で有料記事を出しても、読者との信頼関係がまだ弱い。まずは無料記事で「読まれる」「反応される」「また読みたいと思われる」状態を作る。

だらだら書きたいことを書くのではなく、毎回の記事で次のどれかを狙う:

- スキされる: 読者が「わかる」「刺さった」と感じる
- フォローされる: 読者が「この人の次の記事も読みたい」と感じる
- 保存される: 読者が「あとで見返したい」と感じる
- コメントされる: 読者が「自分のこととして反応したい」と感じる

有料記事は、この反応が積み上がった先に置く。無料記事の時点で読者の現在地を言語化できていないなら、有料部分を作るより先に、タイトル、冒頭、問い、読後の持ち帰りを改善する。

無料記事では、読者の悩みの言語化・問題の整理・考え方の入口までを渡す。有料記事では、診断、チェックリスト、具体例、手順、テンプレート、個別ケースへの当てはめなど、読者が自分で使える実践部分を渡す。

### 有料化の形式を先に決める

有料化には大きく2種類ある。記事を書く前に、どちらで売るのかを決める。

1. 記事だけで有料にする型
2. 記事に加えて、特典を付ける型

記事だけで有料にする型では、有料本文そのものが商品になる。無料部分で問題意識と見取り図を作り、有料部分で具体的な判断基準、手順、例、深い解説まで読ませる。

特典を付ける型では、有料本文は「なぜそれが必要か」「どう使うか」「どんな順番で考えるか」を説明する本編になる。特典は、読者が実際に手を動かすための道具にする。

特典に向いているもの:

- チェックリスト
- 診断シート
- 質問リスト
- ワークシート
- テンプレート
- 具体フレーズ集
- プロンプト集
- 事例集
- ロードマップ

### 特典付き有料記事という選択肢

有料記事は、本文だけで完結させる形に限らない。購入後にメールアドレス登録フォームへ案内し、チェックシートやドキュメント類をダウンロードできる形にする設計もある。参考記事では、この導線にメルマガ登録も組み込まれていた。

ただし、このスタイルガイドでは記事構成を優先する。特典やメルマガ導線は、あくまで有料化の選択肢として考える。記事本文では、まず読者の悩みを言語化し、本文を読む理由を作る。特典を付ける場合も、売り込みを前面に出しすぎず、「読んだ内容を実践するための補助」として自然に置く。

メール登録やメルマガ登録を含める場合は、受け取れるものと登録される内容をわかりやすく書く。購入者が「知らないうちに登録された」と感じないようにする。

特典付きにする場合、無料部分で特典を強く売り込みすぎない。まず読者の問題を言語化し、「これは自分に必要だ」と感じてもらう。そのうえで、有料部分や購入案内で「実際に整理するためのシートも付けている」と自然に示す。

### パターン1: 違和感解体型

#### 目的

読者がうまく言葉にできていないモヤモヤを先に言語化し、「それ、自分も感じていた」と思わせる。読者の違和感を入口にして、背景にある構造や前提のズレを解体する。

#### 使う場面

- AI、働き方、人間関係、人生後半、発信、学びなど、読者が薄く不満や疲れを感じているテーマ
- 一般論では語られているが、読者の実感とズレているテーマ
- 「なぜかしっくりこない」「頑張っているのに違和感が残る」状態を扱う記事

#### タイトルの型

```
なぜ、〇〇すると△△な違和感が残るのか
〇〇がうまくいっているはずなのに、なぜ満たされないのか
〇〇に疲れる本当の理由
```

#### 冒頭構成

1. 読者が感じていそうな違和感を、具体的な場面で出す
2. 「でも、理由がうまく説明できない」という状態を代弁する
3. よくある説明を一度出し、「たぶん問題はそこじゃない」とずらす
4. この記事で解体する核心の問いを提示する

#### 本文構成

1. 違和感が起きる典型的な場面を並べる
2. よくある原因説明を検討する
3. それだけでは説明できない部分を示す
4. 本当の原因を、自分の観察や体験から再定義する
5. 読者が明日から見方を変えられる視点に落とす

#### 無料・有料の境界

無料部分では、違和感の言語化と原因の方向性までを出す。有料部分では、読者自身の状態を判定するチェック項目、具体的な改善手順、ケース別の対処、使える言い換え例まで入れる。

記事だけで有料にする場合は、有料本文の中でチェック項目や対処例まで説明する。特典付きにする場合は、有料本文で考え方を説明し、特典として「違和感の正体を整理する診断シート」「ケース別の言い換え集」などを付ける。

#### 例タイトル

- AIに文章を書かせるほど、自分の文章ではなくなる理由
- 人間関係を減らしたのに、なぜ孤独は軽くならないのか
- ちゃんと休んでいるのに疲れが取れない人が見落としていること

### パターン2: 分岐比較型

#### 目的

うまくいく人とうまくいかない人の差を見せることで、読者に「自分はどちら側だろう」と確認させる。単なるノウハウではなく、成果が分かれる前提条件や考え方の違いを明確にする。

#### 使う場面

- note、AI活用、発信、仕事術、学び直し、老後準備など、成果差が見えやすいテーマ
- 「同じことをしているのに結果が違う」構造を扱う記事
- 有料部分で診断、分類、ロードマップを出したい記事

#### タイトルの型

```
なぜ、〇〇できる人と、何度やっても△△できない人に分かれるのか
〇〇で成果が出る人と、空回りする人の違い
同じ〇〇をしているのに、結果が分かれる理由
```

#### 冒頭構成

1. うまくいく人とうまくいかない人の対比を出す
2. 読者がやっていそうな努力を具体的に挙げる
3. 「努力不足ではない」と一度救う
4. 差がつくのは、もっと手前の前提や設計にあると示す

#### 本文構成

1. A側とB側の違いを、行動ではなく前提から比較する
2. 読者が誤解しやすいポイントを示す
3. 結果が出る人の見ている順番を説明する
4. 自分の経験や観察で裏づける
5. 読者が今どちら側にいるか確認できる形にする

#### 無料・有料の境界

無料部分では、成果が分かれる理由と大きな見取り図までを出す。有料部分では、自己診断、タイプ別の処方箋、優先順位、具体的な実践ステップ、テンプレートを置く。

記事だけで有料にする場合は、有料本文でタイプ分類と処方箋まで読ませる。特典付きにする場合は、有料本文で分岐の考え方を説明し、特典として「自己診断シート」「タイプ別ロードマップ」「優先順位チェックリスト」などを付ける。

#### 例タイトル

- AIを使って思考が深くなる人と、文章が薄くなる人の違い
- noteを書き続けて読まれる人と、埋もれる人の違い
- 定年後に軽くなる人と、ますます不安になる人の違い

### パターン3: プロセス公開型

#### 目的

完成物だけではなく、「どう考えたか」「どこで迷ったか」「どう判断したか」を見せる。読者に、結果ではなく思考の手順を持ち帰ってもらう。

#### 使う場面

- 記事作成、AI活用、企画、意思決定、発信設計、人生の選択など、過程そのものに価値があるテーマ
- 自分の試行錯誤を、読者の再現可能な手順に変換したい記事
- 有料部分でプロンプト、チェックリスト、作業ログ、判断基準を出したい記事

#### タイトルの型

```
〇〇する前に、私が必ずやっている問いの整理
〇〇を作るまでに考えたことを、全部分解してみた
私が〇〇で迷ったときに使っている判断基準
```

#### 冒頭構成

1. 完成物や結論を先に少し見せる
2. その裏側にあった迷い、失敗、判断を出す
3. 「大事なのは完成物より、そこに至る順番」と示す
4. この記事ではプロセスを分解すると宣言する

#### 本文構成

1. 最初の問題意識や目的を明確にする
2. 途中で考えた選択肢を並べる
3. 採用しなかった案と、その理由を書く
4. 最終的な判断基準を言語化する
5. 読者が自分のテーマに応用できる手順にまとめる

#### 無料・有料の境界

無料部分では、考え方の流れと判断の大枠を見せる。有料部分では、実際に使った問い、プロンプト、作業手順、失敗例、修正前後、読者がそのまま使えるテンプレートを置く。

記事だけで有料にする場合は、有料本文の中でプロセスの細部、判断理由、修正前後まで見せる。特典付きにする場合は、有料本文でプロセスの意味を説明し、特典として「実際に使った問いリスト」「プロンプト集」「作業テンプレート」「判断基準シート」などを付ける。

#### 例タイトル

- AIで記事を書く前に、私が必ずやっている問いの整理
- 売れるnoteの構成を作るまでに考えたことを分解してみた
- 人生後半のテーマを記事にする前に、私が捨てた問いと残した問い

## 以下は記事評価のサンプル（現時点では採用しない）

### TYPE A: 体験レビュー型（ClaudeCowork記事）
1. 「実はいまこういう実験してます」で始める
2. 時系列で体験を語る（臨場感重視）
3. 使い方をステップ化してまとめる
4. 「なぜこれがすごいのか」を技術的に解説
5. 事業・哲学に接続する

### TYPE B: 哲学・思想型（愛の証明記事）
1. 根源的な問いを投げる（「愛って何？」）
2. 既存の答えを片っ端からぶった切る（歴史的レビュー）
3. 「それだけでは足りない」と結論
4. 「わたしならこう置き直す」と独自の定義を提示
5. その定義であらゆる事例を説明してみせる
6. 哲学・事業に着地
7. 「あなたもそう思いませんか」で締める

### TYPE C: 会社ストーリー型
1. 「久しぶりに書いてます」的な距離感で始める
2. 自分の人生ストーリーを時系列で語る
3. ストーリーの中で哲学が形成される過程を見せる
4. 哲学 → 事業 → ビジョンの順で展開
5. 「力を貸してください」で締める

### TYPE D: ビジョン・プロダクト型（入口が強い記事）
1. 「最近こんなことがあった」で始める（ラスベガス等）
2. 業界の現状を分析して、既存の見方だけでは足りないと示す
3. 自社の独自ポジションを明確化
4. 新概念を定義・説明
5. 具体的なユースケースで読者に想像させる
6. 哲学的な意味づけ → 壮大なビジョン

## 締めのパターン

1. ひとつのきっかけになるようなものであればうれしいです
2. 機械的な「スキ」「フォロー」CTAは必須にしない
3. 読者交流を前提にせず、記事単体で自然に終える

### 必ず含める要素
1. 読者への呼びかけ（「あなたはどうですか」のスタンス）
2. P.S. / P.P.S. / P.P.P.S. は使わない

## noteエディタのフォーマット制約

noteのテキストエディタで使える記法は以下のみ。記事を書くときはこの制約内で書くこと。

| 記法 | ショートカット | 備考 |
|------|--------------|------|
| 見出し | `# ` + スペース | 大見出し。noteでは `##` 以降の見出しレベルはない |
| 小見出し | `## ` + スペース | 小見出し。`###` は使えない（noteでは反映されない） |
| 箇条書きリスト | `- ` or `+ ` or `* ` + スペース | |
| 番号付きリスト | `1. ` or `2) ` + スペース | |
| 引用ブロック | `> ` or `>> ` + スペース | |
| 太字 | テキスト選択 → B | `**太字**` のMarkdown記法は使えない |
| 区切り線 | `---` | |

### 重要な制約

- **`###` 以下の見出しは使えない**: noteでは `#`（見出し）と `##`（小見出し）の2段階のみ
- **太字のMarkdown記法 `**text**` は使えない**: noteエディタ上ではテキスト選択 → Bで太字にする
- **テーブル（表）は使えない**: noteのエディタにはテーブル機能がない。代わりに箇条書きや本文で表現する
- **コードブロックは使えない**: `` ``` `` 記法はnoteに存在しない
- **画像はエディタ上で挿入**: Markdownの `![alt](url)` は使えない

### 下書きファイルの書き方ルール

下書きMarkdownファイルでは `**太字**` や `###` を使ってOK（読みやすさのため）。
ただし、**noteに貼り付けるときに以下の変換が必要**であることを意識する:

- `###` → `##` に変換（noteには2段階しかない）
- `**太字**` → noteエディタ上で手動で太字にする
- テーブル → 箇条書きに変換
- コードブロック → 引用ブロック or 本文に変換

## NGパターン（これをやったらMaloncafeぽくない）

- 「〜させていただきます」的な丁寧すぎる敬語
- 一文が80文字を超える長文
- 見出しが「1. はじめに」「2. 本論」みたいな教科書スタイル
- 太字が全く使われていない
- 1行ごとの改行で余白が多すぎる
- 段落が長すぎて読みにくい
- 体験談やエピソードが一切ない
- 「笑」を入れる
