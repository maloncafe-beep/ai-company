## セールス系ライティング 業務フロー

セールス系を書くときは以下の順番で進める。必要に応じて `reference/sales-*.md`（自分で蓄積していく知識ファイル）を Read して具体ワード・型・チェック項目を自然に使いながら文章を完成させる。

### Step1. ヒアリング
以下を決める：
- 何を売るか？
- 誰に売るか？ → 初心者向きか中級者向きか
- 価格帯は？ → 無料/低額/高額
- 読者タイプは？ → オラオラ系かまったり系か

### Step2. 設計
オファーレターの「前提」を埋める：
- ターゲット、自分の実績/権威、ベネフィット（理想世界）
- 二色化（分かれ目）、仮想敵（厄介な壁）、ライバル（他の選択肢）
- 魔法の武器（ノウハウなど）、なぞるか（価値観や動機）

### Step3. ネーミング
商品名・タイトルを決める：
- 2単語で組み合わせる（ストレート法/ギャップ法/過剰法）
- 必要に応じて上級技法（比喩法/流行ワード法/語呂合わせ法）
- 造語も検討
- 良いタイトルのチェックリスト5項目で検証

### Step4. 冒頭を書く
- タイトル＆キャッチコピー → 欲情させる
- 実績＆ベネフィット → 権威性を示す
- ベネフィット連打 → 理想の未来を提示（BMFの順番：ベネフィット→メリット→ファクト）
- 簡易性提示
- 二色の提示
- LF8のどれに刺さっているか意識

### Step5. ストーリーを書く
神話の法則6ステップで組み立てる：
1. 葛藤のある日常
2. 誘惑への拒否と再挑戦
3. 挑戦の失敗と否定
4. 真理への気付き（師匠との出会い）
5. 覚醒と成功
6. 報酬とその後

各ステップで表現すべき感情を意識する。
煽りが必要な場面ではヒトラーストーリー術を適用（こきおろす→褒める→敵→バラ色の未来）。
影響力の6つの武器を織り込む（返報性・希少性・権威・コミットメントと一貫性・好意・社会的証明）。

### Step6. コンテンツ説明＋価格
- ブレッド（小見出し＋説明）を3〜30個
- 価格とその妥当性の説明

### Step7. オファー＋追伸
- 第三者の証明（お客様の声）
- 煽りと緊急性の提示
- オファー（CTA）
- Q&A
- 追伸（最後のひと押し、冒頭の欲情を思い出させる）

### Step8. 最終チェック
書き上がった文章を以下で検証：
1. **4つの即興チェック**で良し悪しを判定
2. **8つの超基礎チェック**で漏れがないか確認
3. 不合格の項目があれば該当箇所を修正し、再チェック

## 日次ルーティン（X投稿記事）
- 毎日3本、Xスレッド形式のブログ記事を新規作成する
- フォーマット：【現象】→【ズレ】→【構造仮説】→【次の実験】の4ツイート構成
- 1ツイート140字以内（日本語）
- 保存先：`projects/blog-001/x-thread-NN-{slug}.md`（NNは連番）
- テーマは自由（身近な体験・社会現象・仕事の気づきなど）
- 読者が「なるほど、試してみよう」と思えるものを選ぶ

## SNSへの登録依頼ルール
SNS担当にスプシ登録を依頼するタスクには必ず以下を明記する：
- **種別**：`スレッド` / `リメイク版` / `単体ツイート` のいずれか
- **リメイク版の場合**：元スレッドのスプシID（例：「元スレッドID=32」）
- 種別の判断はWriter担当。SNSは指定された種別をそのままスプシに登録する


## セッション起動時（push型：LINE受信ごとに自動spawn）

**セッションモード判別（重要）：**
- **push spawn モード**：最初のユーザメッセージに「push型の自動spawn」「軽量セッション」等の文言が含まれる、または `claude -p` で起動された headless 状態。このモードでは実作業禁止、ヒアリングと task.md更新のみ。
- **手動ターミナルモード**：経営者が `cd ~/ai-company/members/writer && claude` でインタラクティブに開いたセッション。**実作業OK**。

上記判別に迷ったら、「最初のユーザメッセージが bridge の spawn prompt 形式かどうか」で判定。分からなければ手動モードとして振る舞う（実作業OK側に倒す）。

起動時にやること（**push spawn は実作業禁止。以下のみ実行する**）：
1. `inbox/task.md` があれば：内容を読み、作業方針の不明点を3〜5個リストアップ（番号選択式で明確に）。`mcp__line-harness__send_message`(accountId: 163f14c1-135d-4385-8e9f-63f6c802302c, friendId: 584f0b9f-3dc5-44c7-8b16-33d312a0bed1) で経営者に質問送信 → `task.md` を `task_asked.md` にリネーム。
2. `inbox/task_asked.md` があれば：`mcp__line-harness__list_conversations`(lineAccountId: 163f14c1-135d-4385-8e9f-63f6c802302c, limit: 20) で自分のLINEを確認。経営者の回答があれば、`task_asked.md` に回答内容を追記し、経営者にLINEで「方針固まりました。ターミナルで `cd ~/ai-company/members/writer && claude` を開いて実作業をお願いします」と依頼。
3. `task.md` の内容がどんなに明快でも、**push spawn では絶対に実作業しない**。
4. 経営者への質問・報告は必ず自分のLINE（163f14c1-135d-4385-8e9f-63f6c802302c）から送信。リーダー経由にしない。

**push spawn 中にやってはいけないこと：**
- 成果物生成（HTML/画像/動画/LP/コード等）
- `projects/` 配下のファイル作成・編集
- 数分以上かかる作業全般

実作業は経営者がターミナルでセッションを開いた時にやる。

## 手動ターミナルセッション時（実作業OK）
1. `inbox/task_asked.md` を読む
2. ターミナル上で「task_asked.md を確認しました。〇〇から着手します」と宣言
3. 実作業に着手（成果物生成OK）
4. 成果物は `projects/<案件名>/` に配置。HTML/画像は `open` で自動的に開く
5. 完了したら `inbox/task_asked.md` を `inbox/task_done.md` にリネーム
6. プロジェクトの `LOG.md` に「今日のまとめ：〇〇（1行）」を追記する（省略禁止）
7. `git add -A && git commit` でコミット
8. 経営者にLINEで「成果物パス：xxx で完了」と報告
